# Airship Control

CC:Tweaked controller for 24 Create Propulsion liquid vector thrusters. It discovers all 24 by peripheral type, including through the wired hub, and calibrates each one independently; it does not assume peripheral suffixes match corner positions. GPS, Avionics heading, yaw rate, and air pressure drive the measured horizontal autopilot. Height uses saved burner amounts through the adjacent Create Redstone Link; there is no altitude PID.

## Install

Controller v1.5.9 tunes for faster cruise using measured thrust, drag, and yaw response. FLIGHT shows live horizontal speed, remaining distance, and a closing-speed ETA on the computer, CC monitor, and DirectGPU monitor; speed and ETA use a rolling four-second GPS window. GPS is corrected from the computer's position to the ship center using its reported two-block aft offset and live heading. During travel the controller holds its starting heading; on arrival it turns in place to the nearest cardinal heading (north, south, east, or west), then holds position and altitude. Pitch/roll do not reduce throttle, speed, or the calibrated power ceiling; keep the physical gyro powered. The controller does not perform an automatic descent or touchdown. FULL AUTO CAL waits for a fresh control-loop sample before starting, checkpoints the fitted model after the 96 thruster/nozzle tests, and saves the final profile only after auto validation. GPU redraw targets 40 Hz, with cooperative yields and native monitor/GPU click support; actual rate depends on display and server performance.

In the computer terminal, install Basalt 2.5, download the updated controller beside it, and run it:

```text
wget run https://basalt.madefor.cc/2.5/install.lua minified
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/airship.lua airship.lua
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/airship-updater.lua?bootstrap=1.3.1 airship-updater.lua
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/pid-tuner.lua pid-tuner.lua
airship.lua
```

Or copy `airship.lua` into a file on the computer and run `airship.lua`. The computer needs wireless GPS access and all 24 `liquid_vector_thruster` peripherals. They can be connected directly or exposed by the wired peripheral hub; their peripheral names and number suffixes can vary. The controller finds them by peripheral type, including mixed direct and hub-connected devices, and stops with a clear count error unless it sees all 24. For accurate altitude readout and burner calibration, connect a Create: Avionics **Altitude Sensor** to the computer through the peripheral network. Height control still comes from burner amounts. Its peripheral type is `altitude_sensor`; the app detects it automatically and falls back to GPS altitude if it is absent.

Install `airship-updater.lua` beside the controller. It validates and installs the controller, both diagnostics, the PID tuner, and itself from one GitHub commit. It keeps each previous copy as a `.bak`, leaves calibration and PID files in place, then launches the controller. To bootstrap the rollback updater from an older install, run `wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/airship-updater.lua?bootstrap=1.3.1 airship-updater-new.lua` then `airship-updater-new.lua`. The temporary bootstrap file can be deleted afterward. Height is controlled only by burner amounts from the saved calibration map.

To check that CC:Tweaked sees it, run `lua` and enter:

```lua
for _, name in ipairs(peripheral.getNames()) do print(name, peripheral.getType(name)) end
```

The app searches both directly attached peripherals and peripherals one Malahit hub deep behind the wired peripheral hub. It reads `altitude_sensor` (`getHeight`, `getVerticalSpeed`, `getAirPressure`), `navigation_table` (`getHeadingRad`) and `gimbal_sensor` (`getAngularRatesRad`, `getGravity`) through either route. GPS still supplies world position. The navigation table heading rotates GPS error and velocity into the ship's current axes, so turning while navigating does not leave the controller steering in the old direction. If heading is unavailable, destination autopilot refuses to engage.

Attach a CC:Tweaked monitor to the ship's peripheral network. The computer screen stays the control and text-entry console. When DirectGPU is available, including over a wired modem as `directgpu_5`, the monitor shows the high-resolution RGB flight panel with touch controls; its layout scales to the detected display size, including a 4-wide by 3-tall monitor wall. Click the **FLIGHT**, **CALIBRATION**, and **HEIGHTS** tabs above the panel to switch views. The HEIGHTS view lists every saved calibration point with its altitude, burner level, and pressure; use **PREVIOUS/NEXT** to browse longer lists and tap a row to select that height. Expose both the DirectGPU and CC monitor on the same wired peripheral network. Display creation targets the exact CC monitor name; it does not search the surrounding world. Enter coordinates, altitude targets, and PID values on the computer itself. With no monitor attached, the computer screen shows the full interface. Check for DirectGPU with `peripheral.find("directgpu")`.

On the full-size computer UI, use **FLIGHT** for navigation and **CALIBRATION** for PID values, direction checks, manual burner control, locking a stable burner level, and the 15–5 sweep. **ALT - / ALT +** moves to the previous or next saved height (wrapping at either end); if no heights are saved, it changes the target by one block. **SAVED ALT** selects the next saved height. The calibration screen's **CLEAR HEIGHTS** button clears saved height data from every view after a second tap within eight seconds. The standard monitor has touch controls for flight and calibration; the DirectGPU panel has separate flight, calibration, and saved-height views, with touch controls for all the main actions. It also shows vertical speed, sensor status, and the current target burner level when calibrated. While a text box is focused, keyboard shortcuts are paused; **Esc** clears focus, and **Enter** submits the current field.

Put a Create Redstone Link transmitter against the computer's **front** (monitor side). Put `create:analog_lever` in both frequency slots on this transmitter and the burner receiver, in the same order. The app sends analog power 0–15 out the computer's front face to control the burners.

## Full autopilot calibration

Connect all 24 `liquid_vector_thruster` devices, working wireless GPS, an Avionics `altitude_sensor`, `navigation_table`, and `gimbal_sensor`. The sensor and thrusters may be exposed through the supported wired/hub routes. Calibration measures the current ship and load; weight and thruster number positions do not need to be entered.

1. Get the ship airborne in a large open area: the faster cruise tests can travel hundreds of blocks from the start. Use a saved height or manual burner level to let it settle at your normal cruising height. Keep the gyroscope powered. Keep enough fuel for at least 40 minutes of automatic movement, allowing for the 24-thruster survey and retries.
2. Open **CALIBRATION** and press **FULL AUTO CAL**, or press **R** on the computer with no text box focused. It starts even if an old calibration already exists. No sweep is started. The current burner level is held throughout the procedure.
3. Let it finish: all 96 thruster/nozzle tests keep their six-second pulses and four-second coast measurement windows. Expect roughly 26 minutes for those measurements at normal sampling speed, plus five automatic travel/braking validation legs; slower hub/GPS sampling increases the time. After the 96 tests the fitted candidate is checkpointed to `airship-autopilot-pending.cfg`. If validation is canceled, fails, or the computer restarts, press **FULL AUTO CAL** again to resume with the five auto tests only. It chooses P/I/D gains from measured response, sample timing, and filtering delay, and estimates cruise speed from thrust and drag up to 20 blocks/second. Excessive overshoot or a failed arrival triggers retuning, with up to five validation passes; pitch/roll do not trigger reduced thrust or recovery retries. A missing sample pauses the calibration; only a gap over eight seconds restarts the active thruster baseline or current validation leg instead of discarding the run. Actual time depends on the ship and server. Watch the displayed stage, remaining position error, and net drift. **CANCEL AUTO CAL**, **HOLD**, or **H** cancels; **STOP/S** also cuts burner output.
4. After **FULL AUTO CAL saved**, select a saved altitude, enter destination `X Z` on the computer, and press **AUTO/A**. The controller brakes using measured response, counters yaw through individual thruster commands, and keeps correcting position after arrival. At arrival it turns in place to the nearest cardinal direction based on the route, then holds position and altitude. It does not automatically lower the ship or touch down; choose a lower saved altitude separately. The calibration finish leaves the burner at its starting level until you choose another height or flight mode.

The measured model, tuned gains, pressure reference, and verification results are saved in `airship-autopilot.cfg` and loaded after restart. The unvalidated thruster model is checkpointed separately; it cannot engage autopilot until the auto tests pass. A failed or canceled run keeps the last working profile and lets **FULL AUTO CAL** resume validation from the checkpoint. Changed peripheral names invalidate the model. Recalibrate after changing mass/cargo, fuel type, thruster placement, propulsion settings, or upgrading to v1.5.0 for the 24-thruster setup. Autopilot learns a running correction for persistent horizontal drift and turning bias, estimates speed from a short position trend, and uses gimbal gravity to measure yaw rate accurately. Yaw drag compensation is bounded so an overestimated drag value cannot turn yaw damping into positive feedback. Validation measures net drift over several seconds and bounds individual position excursions. Calibration models horizontal movement and yaw, not active roll/pitch leveling; the gyro handles pitch/roll but does not hold heading. The optional **DIR CHECK/C** button only sends the old four wiring-check pulses and does not replace FULL AUTO CAL.

After updating to v1.5.0 or later, run FULL AUTO CAL once to rebuild the model for all 24 thrusters and replace the previous speed/power ceiling. Old profiles with the previous eight thruster names will be rejected automatically. The 12 blocks/second controller cap is now 20; the real ship may be limited by its measured thrust, drag, fuel, and braking distance.

### Air pressure

Calibration measures drag at its current pressure. Autopilot scales that learned drag estimate with the live pressure reading and actively brakes instead of relying on coasting to stop. In thinner air it eases position/velocity feedback to avoid exciting rocking with delayed GPS readings; the calibrated cruise target remains available. Both checked pack configs have `useAtmosphericPressure = false`, so this controller does not apply an invented inverse-pressure thrust boost. If the server changes that setting, or you fly under substantially different conditions, recalibrate at the intended cruise height. Pressure compensation is a learned approximation, not a guarantee across every altitude.

### Controls and manual gains

**G** focuses destination entry, **Y** focuses height entry, **P** cycles saved heights, **A** engages autopilot, **H** holds/cancels calibration, and **S** cuts outputs. **Esc** clears text focus. Height remains controlled by the burner map; FULL AUTO CAL does not generate or change that map. Run the separate sweep only when you need new saved heights.

FULL AUTO CAL chooses P, I, and D automatically. Manual **SET PID** overrides are saved into the active profile; use the displayed measured gains as the starting point. Accepted ranges are P `0.0001–1`, I `0–0.05`, D `0–4`. Re-running full calibration replaces manual overrides with newly measured and tested gains. The older `airship-pid.cfg` applies only before a measured profile exists; the standalone PID tuner is for the legacy controller and directs measured-profile users back to FULL AUTO CAL.

## Manual burner calibration

Press **M** or **MANUAL M** to hold a fixed burner signal. **Up/Down** changes the signal by one from 0–15; the screen shows the current burner signal and average normalized thrust. To automatically record levels **15 down to 5**, put the ship in clear air, choose a safe starting height, then press **V** twice within 8 seconds (or tap **SWEEP** twice on the DirectGPU monitor). The app ramps toward each signal at no more than six redstone levels per second, then saves its signal and altitude after vertical speed stays below 0.12 blocks/sec for four seconds. It skips a level if it cannot settle within 45 seconds. The sweep no longer stops based on vertical speed or distance traveled; it still stops if GPS/pressure is lost or saving fails. The last stop reason and saved/skipped counts stay visible for 15 seconds, and previously saved levels remain. After the sweep it resumes altitude hold at the current height. **K** or **LOCK LEVEL** still saves one manually stabilized signal. Saved altitude-to-signal points are interpolated; when calibration data exists, altitude hold uses the mapped burner signal directly without PID trimming. The burner output still slews toward that signal.

Press **M** again to leave manual mode; burner output follows the selected saved height. **P** or **SAVED ALT** cycles through calibrated altitudes, sorted low to high. If no calibration points are saved, automatic height selection has no mapping; use manual burner control until you calibrate. The sweep covers signals 15 through 5; it does not test 0–4.

The DirectGPU redraw loop targets 40 Hz. Avionics and wired control run in a separate cooperative loop with a 0.2-second delay between passes; actual sample timing includes GPS and peripheral latency. GPS lookups wait up to two seconds, and a fix must be absent for over six seconds before navigation is stopped, allowing brief wireless dropouts to recover. Autopilot requires fresh heading, yaw, and pressure readings and must be re-engaged after navigation data is lost. FULL AUTO CAL begins on the next fresh control-loop sample instead of rejecting a click between sensor updates; zero pressure produces a specific diagnostic. During full calibration, missing/stale navigation samples pause commands; only gaps over eight seconds restart the current thruster baseline or validation leg, allowing slower wired-hub sample cycles to finish the measurement. The controller does not detect obstacles or land the ship. Successful simulated checks do not replace testing the actual craft.

## DirectGPU startup hang: notes for future agents

Reported symptom: the computer remained at `Setting up display...` for minutes after the 24-thruster update. The confirmed controller defect was unbounded GPU setup before UI construction, followed by repeated setup attempts on failure. The progress message also covered the later UI construction, so that message alone never proved which GPU method stalled. Earlier claims that wired DirectGPU itself was definitely the cause were not verified in the running game.

History matters: v1.5.0 (`3a7f2b1`) did not change GPU setup from v1.4.2. Older commits repeatedly disabled and enabled it: `aeffe66` disabled GPU, `46b262a` enabled it with slower rendering, `4eb5381` blocked remote GPU, and `911a914` allowed wired GPU again. `bff1bab` added cooperative yields and progress messages, and `353bdd3` enabled mouse events. v1.5.1 disabled GPU globally; v1.5.2 simply enabled it again. Neither flag change established or fixed the underlying wait.

v1.5.3 keeps GPU enabled by default and gives setup an eight-second deadline through CC's `parallel.waitForAny`. Each step is printed and written to `airship-gpu.log` (replaced on each attempt). A setup error or a peripheral wait that exceeds the deadline disables retries for that run, reports the exact step, and opens the CC monitor fallback. Normal setup reuses an existing display (including ID `0`), creates at resolution scale `1` only when needed, checks positive pixel dimensions, and enables mouse events. `Building controls...` and `Starting flight panel...` distinguish later startup phases. Restarting the controller tries GPU again; no flight or burner calibration files are removed.

The local server-pack snapshot contains `directgpu-1.0.25-neoforge-1.21.1.jar`. Inspection of its `DirectGPUPeripheral` bytecode confirms `listDisplays`, `getDisplayInfo`, `autoDetectAndCreateDisplayWithResolution(1)`, and `enableMouseEvents(id,true,false)` match this setup. The create method accepts scale `1`; mouse setup returns void, so successful `pcall` is sufficient. This is evidence about the local snapshot, not confirmation of the active server version or an in-game reproduction.

The deadline works when a peripheral call yields while waiting for CC/server events. Lua cannot interrupt a Java method that blocks the entire computer thread without yielding. If that occurs, recover with Ctrl+T (or a computer reboot) and run `airship.lua --no-gpu` for one session, then inspect `airship-gpu.log` to find the last attempted method. If GPU reaches `ready` but startup still stalls, use the later phase messages to investigate UI construction or event-loop startup. Do not blanket-disable wired GPU or remove yielding checkpoints as a speculative fix. A native blocking method requires a mod-level investigation; this script does not patch the mod.

The next screenshot from v1.5.3 stopped specifically at `GPU: create display at resolution 1`, before `getDisplayInfo` or `enableMouseEvents`. That narrows the stalled call to unnamed `autoDetectAndCreateDisplayWithResolution(1)`. The eight-second Lua deadline did not resolve the reported stall. Bytecode inspection explains a costly path in that call: `resolveCreateMonitor` without a string argument invokes `detectNearestMonitorInfo(4)`, which invokes `autoDetectMonitorsInternal`. That method enumerates wired monitors and still loops over offsets -32 through 32 on all three axes, checking the radius-32 sphere for physical monitors. It may inspect a large region and repeatedly determine monitor geometry. The screenshot establishes the stalled API call; the exact internal operation still has not been profiled in the live game.

v1.5.4 bypasses that broad scan: it gets the discovered CC monitor's exact peripheral name and calls `autoDetectAndCreateDisplayWithResolution(monitorName, 1)`. In the inspected JAR, a nonempty string takes `detectNamedMonitor` instead of the broad nearest-monitor scan. The monitor name must be visible to DirectGPU on the wired network. Existing valid displays are still reused. If no exact monitor name is available, setup falls back with an explicit wiring message instead of calling the unnamed overload. Failed creation no longer calls `autoDetectMonitor` for diagnostics, since that would repeat the broad scan. Preserve these restrictions in future changes: no implicit unnamed fallback on creation failure. Regression tests check exact name and scale arguments and ensure failure never starts that diagnostic scan. In-game confirmation is still needed; the Java-call limitation above remains relevant.

Regression checks run from the repository root with Lua 5.2+: `lua airship/tests/gpu-startup.lua`, `lua airship/tests/yielding.lua`, and `lua airship/tests/navigation.lua`. They cover new/reused display zero, resolution, cooperative setup timeout, malformed info, mouse setup failure, peripheral yielding, click routes, all display tabs, interrupted frames, and simulated navigation. They cannot establish actual GPU output, server timing, or flight behavior in Minecraft. Report those separately when publishing a fix.

## Legacy diagnostic script

FULL AUTO CAL above is the current calibration and tuning path. The standalone diagnostic below runs the older uniform-thruster steering model, not the measured mixer, so its results do not validate the new autopilot. Keep it for inspecting legacy behavior and producing logs.

In a large, obstacle-free area, stop the controller with **Ctrl+T**, then install and start the diagnostic:

```text
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/diagnostic.lua diagnostic.lua
diagnostic.lua
```

After a diagnostic run containing all four X/Z autopilot legs, stop the controller and run `pid-tuner.lua`. It reviews the latest CSV and suggests modest horizontal P/D changes; confirm to save them, then restart the controller and repeat the test. It does not drive the ship itself.

The ship front faces east. It asks for ship size, balloon capacity, burner count and fill, and mass/load. Once you finish entering the data, it requires all 24 `liquid_vector_thruster` devices, including devices exposed through the peripheral hub, and individually pulses each one on both vector axes. The computer reports each full hub path/name with its measured relative X/Z movement and includes those readings in the CSV; it does not assume peripheral number suffixes match thruster positions. The diagnostic then runs four autopilot moves to points 10 blocks away (X+, X−, Z+, Z−). The CSV records horizontal PID gains, burner signal, thruster commands and readings, altitude, pressure, heading, yaw rate, relative GPS position, and velocity. Absolute GPS coordinates are not recorded. Height control uses saved burner amounts only; there is no altitude PID. GPS loss still ends the test because navigation data would no longer be valid; **Q** also aborts. On exit it turns off thrusters and restores the burner signal that was active before the test. It saves a new CSV without overwriting older logs, then automatically uploads it using CC:Tweaked's built-in `pastebin put` program to a **public** Pastebin paste. HTTP access must be enabled.

The prompts default to the facts provided so far: 15x15 footprint, 845 blocks of balloon capacity (please verify), four burners, and 210 max fill each. It calculates combined usable fill as the smaller of balloon capacity and burner capacity (840 with those defaults). Correct any value that differs on the ship. Run only where the ship can move freely and stay at the controls; there is no speed, altitude, or distance cutoff.
