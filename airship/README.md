# Airship Control

CC:Tweaked controller for 24 Create Propulsion liquid vector thrusters. It discovers all 24 by peripheral type, including through the wired hub, and calibrates each one independently; it does not assume peripheral suffixes match corner positions. GPS, Avionics heading, yaw rate, and air pressure drive the measured horizontal autopilot. Height uses saved burner amounts through the adjacent Create Redstone Link; there is no altitude PID.

## Install

Controller v1.7.20 follows a fixed straight route with independent sideways correction and a stopping-distance speed plan. It accelerates as available thrust and stopping distance allow on long routes, brakes before the destination, and blends into precise position hold for arrival. Measured thrust, drag, yaw response, and sensor delay determine its commands. Retry caution now increases stopping-planner conservatism without slowing the steering feedback loop; this addresses the cause of the long lateral drift and terminal settling seen with profiles at maximum caution. The FLIGHT view shows elapsed autopilot time, which freezes when **DESTINATION REACHED** appears. Press **Alt+=** / **Alt+-** (or keypad **Alt+** / **Alt-**) to adjust burner strength by one while flying; this overrides vertical burner control without canceling horizontal autopilot. Target height is shown only when one is known. With an Advanced Peripherals Chat Box, only `pro_hacker_noob` can use `seat up` / `seat down` in public chat or `$seat up` / `$seat down` as hidden messages. These commands use a Create Sequenced Gearshift peripheral and three Create: Avionics laser sensors: `seat down` lowers the seats to the lowest sensor's ground clearance minus 2 blocks; `seat up` reverses that exact travel. The controller refuses to move unless all three sensors report a valid hit, and saves the travel distance for the return command. Create's sequenced gearshift controls the distance; at 96 RPM a rope pulley travels about 3.75 blocks/second. Existing flight calibration files remain compatible. **BRAKE CAL / F6** adds eight stopping measurements to a completed 96-test thruster survey, adjusting stopping distance for live pressure and polling time. It can run before the five flight tests pass. Until that succeeds, the previous braking planner remains active. The saved cruise estimate sizes validation flights; modern profiles have no fixed forward cruise cap. FLIGHT shows live horizontal speed, remaining distance, and a closing-speed ETA on the computer, CC monitor, and DirectGPU monitor; speed and ETA use a rolling four-second GPS window. GPS is corrected from the computer's position to the ship center using its reported two-block aft offset and live heading. During travel the controller holds its starting heading; on arrival it turns in place to the nearest cardinal heading (north, south, east, or west), then holds position and altitude. The final heading is the closest of 0, 90, 180, or 270 degrees to the actual heading at arrival. Pitch/roll do not reduce throttle, speed, or the calibrated power ceiling; keep the physical gyro powered. The controller does not perform an automatic descent or touchdown. FULL AUTO CAL waits for a fresh control-loop sample, checkpoints the fitted model after the 96 thruster/nozzle tests, and saves the final profile only after auto validation. Overshoot during a flight test is recorded but no longer forces that leg to repeat; validation still requires settling at the waypoint and holding it. Timeouts still retry. Each flight now gets its own dated CSV under `flight logs/`, recorded at up to 2 Hz for ten minutes. After the ship is stationary or held, press **F8** to mark the report saved and show its path; F8 never uploads it.

After a normal flight, press **H** if it is still moving, then **F8**. The report is saved in `flight logs/flight-YYYY-MM-DD_HH-MM-SS.csv`; F8 shows the exact filename on screen. Logs contain relative GPS coordinates, sensor readings, the autopilot's requested/allocated acceleration, braking state and each thruster command. They record up to 1,200 samples (ten minutes at 2 Hz), then stop to bound disk use. No Pastebin or other upload is used. To find the reports later, run `ls "flight logs"` from the computer terminal.

In the computer terminal, install Basalt 2.5, download the updated controller beside it, and run it:

```text
wget run https://basalt.madefor.cc/2.5/install.lua minified
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/airship.lua airship.lua
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/airship-updater.lua?bootstrap=1.3.6 airship-updater.lua
wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/pid-tuner.lua pid-tuner.lua
airship.lua
```

Or copy `airship.lua` into a file on the computer and run `airship.lua`. The computer needs wireless GPS access and all 24 `liquid_vector_thruster` peripherals. They can be connected directly or exposed by the wired peripheral hub; their peripheral names and number suffixes can vary. The controller finds them by peripheral type, including mixed direct and hub-connected devices, and stops with a clear count error unless it sees all 24. For accurate altitude readout and burner calibration, connect a Create: Avionics **Altitude Sensor** to the computer through the peripheral network. Height control still comes from burner amounts. Its peripheral type is `altitude_sensor`; the app detects it automatically and falls back to GPS altitude if it is absent.

Install `airship-updater.lua` beside the controller. It validates and installs the controller, both diagnostics, the PID tuner, and itself from one GitHub commit. It keeps each previous copy as a `.bak`, leaves calibration and PID files in place, then launches the controller. To bootstrap the rollback updater from an older install, run `wget https://raw.githubusercontent.com/eranfeldman/cc-tweaked/main/airship/airship-updater.lua?bootstrap=1.3.1 airship-updater-new.lua` then `airship-updater-new.lua`. The temporary bootstrap file can be deleted afterward. Height is controlled only by burner amounts from the saved calibration map.

To check that CC:Tweaked sees it, run `lua` and enter:

```lua
for _, name in ipairs(peripheral.getNames()) do print(name, peripheral.getType(name)) end
```

The app searches both directly attached peripherals and peripherals one Malahit hub deep behind the wired peripheral hub. It reads `altitude_sensor` (`getHeight`, `getVerticalSpeed`, `getAirPressure`), `navigation_table` (`getHeadingRad`), `gimbal_sensor` (`getAngularRatesRad`, `getGravity`), three `laser_sensor` peripherals (`getClosestHitDistance`), and the Create `Create_SequencedGearshift` through either route. GPS still supplies world position. The navigation table heading rotates GPS error and velocity into the ship's current axes, so turning while navigating does not leave the controller steering in the old direction. If heading is unavailable, destination autopilot refuses to engage.

Attach a CC:Tweaked monitor to the ship's peripheral network. The computer screen stays the control and text-entry console. When DirectGPU is available, including over a wired modem as `directgpu_5`, the monitor shows the high-resolution RGB flight panel with touch controls; its layout scales to the detected display size, including a 4-wide by 3-tall monitor wall. Click the **FLIGHT**, **CALIBRATION**, and **HEIGHTS** tabs above the panel to switch views. The HEIGHTS view lists every saved calibration point with its altitude, burner level, and pressure; use **PREVIOUS/NEXT** to browse longer lists and tap a row to select that height. Expose both the DirectGPU and CC monitor on the same wired peripheral network. Display creation targets the exact CC monitor name; it does not search the surrounding world. Enter coordinates, altitude targets, and PID values on the computer itself. With no monitor attached, the computer screen shows the full interface. Check for DirectGPU with `peripheral.find("directgpu")`.

On the full-size computer UI, use **FLIGHT** for navigation and **CALIBRATION** for PID values, direction checks, manual burner control, locking a stable burner level, and the 15–5 sweep. **ALT - / ALT +** moves to the previous or next saved height (wrapping at either end); if no heights are saved, it changes the target by one block. **SAVED ALT** selects the next saved height. The calibration screen's **CLEAR HEIGHTS** button clears saved height data from every view after a second tap within eight seconds. The standard monitor has touch controls for flight and calibration; the DirectGPU panel has separate flight, calibration, and saved-height views, with touch controls for all the main actions. It also shows vertical speed, sensor status, and the current target burner level when calibrated. While a text box is focused, keyboard shortcuts are paused; **Esc** clears focus, and **Enter** submits the current field.

Put a Create Redstone Link transmitter against the computer's **front** (monitor side). Put `create:analog_lever` in both frequency slots on this transmitter and the burner receiver, in the same order. The app sends analog power 0–15 out the computer's front face to control the burners.

## Cruise controller and upgrades

### v1.7.14 Elapsed flight timer

FLIGHT shows elapsed time from AUTOPILOT engagement through the final cardinal turn. The timer freezes at the first `DESTINATION REACHED` state and resets when a new flight starts or the current flight is canceled. The timer appears in the computer/DirectGPU flight details and CC monitor telemetry.

### v1.7.15 Burner hotkeys and altitude target display

Alt+= / Alt+- adjusts the burner output by one, from 0 to 15, without stopping horizontal autopilot. These keys are disabled while stopped or calibrating. The flight displays omit target altitude when no target is available.

### v1.7.20 Distance-based seat pulley commands

`seat down` uses the nearest ground hit from all three `laser_sensor` peripherals, subtracts a 2-block clearance, and commands the Create Sequenced Gearshift's `move(distance, 1)` API. `seat up` calls `move` with the same distance and modifier `-1`. The completed travel distance persists in `airship-seat-distance.cfg`, so a controller restart does not lose the return distance. Commands are owner-only and still accept public or `$` hidden Chat Box messages. A regular Create Gearshift only reverses rotation; connect a **Sequenced Gearshift** as a CC peripheral for bounded travel. At 96 RPM, Create's pulley conversion is 96/512 blocks per tick, or 3.75 blocks/second at 20 TPS.

### v1.7.16 Owner-only seat chat commands (superseded)

With an Advanced Peripherals Chat Box and a CC Redstone Link Bridge connected to the computer's peripheral network, the chat listener accepts only exact `seat up` / `seat down` commands from username `pro_hacker_noob` (case-insensitive). Both public messages and hidden `$seat up` / `$seat down` messages work. The bridge sends strength 15 or 0 on the frequency pair `minecraft:stick`, `minecraft:oak_button`; it replies privately to the authorized player. Other players and other text are ignored.

### v1.7.19 Max lift control

The FLIGHT screen now has a **MAX LIFT** button on the computer, CC monitor, and DirectGPU monitor. It cancels active autopilot/calibration, holds the current burner setting, points all 24 horizontally mounted vector thrusters to maximum downward gimbal (`setVector(0, -1)`), and runs them at full normalized throttle. Press **HOLD** or **STOP** to exit. The mod limits gimbal travel to about 30 degrees from each thruster's mounted direction; this is maximum downward vectoring, not a vertical nozzle rotation.

### v1.7.18 Chat Box event argument order

Advanced Peripherals 0.8 sends Chat Box events as `(event, UUID, username, message, ...)`; the previous controller read the UUID as the username, so it ignored valid commands. The listener now reads the documented argument order and also accepts the older `(event, username, message, ...)` form. It continues to accept only `pro_hacker_noob` and exact seat commands.

### v1.7.17 Hub chat feedback

Chat commands retry bridge and Chat Box discovery when received. The controller displays `CHAT RX` for an unrecognized message from the authorized player, `CHAT OK` when it sent a signal, and `CHAT ERROR` when no bridge is available or the send call fails. Startup prints whether it found each peripheral.

### v1.7.13 Keep retry caution out of steering response

The previous loop multiplied the retry-caution scale into steering response time. The supplied flight profile had `responseScale=4` and a 4.46-second measured delay, making lateral/velocity corrections respond over 11.6 seconds; the log showed a 58-block cross-track excursion and a near-target pass followed by more than two minutes of settling. Retry caution remains in the stopping planner, while steering uses the measured response time directly. Saved 96-test, brake, height, and PID data remain compatible; no recalibration is required.

### v1.7.12 Local dated flight logs

F8 now finalizes the current flight report locally in `flight logs/` and displays its dated CSV path. The controller no longer opens a Pastebin upload tab. Each flight keeps up to 1,200 samples at no more than 2 Hz (ten minutes); longer flights are marked as truncated when F8 is pressed. Reports remain separate instead of replacing the previous flight log. The flight logger still records while the autopilot or full calibration is active; press F8 only after holding or reaching the destination.

### v1.7.9 Shorter brake-calibration runs

The first four BRAKE CAL runs now target half the estimated cruise speed and the second four target cruise speed, instead of testing at cruise speed and twice cruise speed. This cuts acceleration and stopping distance substantially while preserving a higher-speed measurement at the intended cruise rate. Existing completed stops remain checkpointed; each stored run records its actual speed.

### v1.7.8 Record valid braking samples immediately

BRAKE CAL now records each valid reverse-deceleration sample as soon as the ship slows, instead of ignoring the first 0.8 seconds. This avoids finishing a fast stop with too few measurements. GPS-invalid samples, readings without forward motion, and stops that fail the existing settling checks still do not count. The first v1.7.8 run discards any older brake checkpoint and repeats all eight stops; the 96-thruster survey and saved heights remain intact. If fitting still fails, the status identifies the direction and whether deceleration or coast samples were missing.

### v1.7.7 Persist completed brake stops

After each stop has settled and passed the existing low-speed/yaw checks, BRAKE CAL atomically saves that completed measurement and the current count to `airship-brake-checkpoint.cfg`. A GPS jump restarts only the unfinished stop. If the computer program restarts, press BRAKE CAL to continue from the saved count, provided the 96-test thruster model still matches. Partial or GPS-invalid stops are never counted as complete, protecting fit accuracy. **H / CANCEL** discards the checkpoint; it is removed after a brake model saves successfully. A failed disk write keeps the in-memory run and reports the checkpoint error.

### v1.7.6 Alternate each brake test direction

The eight runs now travel +X, -X, +Z, -Z, then repeat the same order at the second speed. Previously the program ran both speeds in one direction before reversing. The saved brake model still combines the two speeds for each direction. This alternating sequence may help isolate GPS faults tied to long one-way runs; it cannot fix an unstable GPS host or server by itself. A regression check verifies the order and fitter pairing.

### v1.7.5 Keep brake-calibration progress through invalid samples

A bad yaw/pressure sample or a test timeout could delete the active BRAKE CAL job. The main loop could then start a new 96-thruster calibration, making the brake count appear to reset after navigation trouble. BRAKE CAL now pauses and retries only the current stop, and a separate mode latch blocks that fallback. Regression checks verify recovery after invalid navigation preserves completed stops.

### v1.7.4 GPS pause preserves brake progress; separate calibration controls

The long-GPS-loss path canceled every calibration after six seconds, deleting the in-memory eight-stop brake job even though the core's shorter interruption handling preserved completed runs. BRAKE CAL now pauses with horizontal commands off and its current burner level held, while retaining the same job, completed runs and recorded count. After a valid GPS fix and fresh navigation readings return, it repeats only the interrupted stop from settling. Missing avionics readings also invalidate only the current measurement. The pause notice reports how many stops are kept. GPS range and jump rejection remain enabled; normal AUTO and FULL AUTO CAL retain their existing GPS-loss behavior.

The GPU calibration menu previously reused the left button's position for BRAKE CAL and CANCEL AUTO CAL. Its click targets were replaced before the new frame was presented, so a still-visible Cancel label could dispatch the new Brake action. The menu now has three permanently separate controls: **BRAKE CAL**, **FULL AUTO CAL**, and **CANCEL**. A frame draws a fixed snapshot of its buttons and publishes their click targets only after successful display presentation. Aborted frames retain the previous visible targets. Duplicate reports of the same click are matched by button bounds across input sources rather than a changing label; the existing short duplicate window and same-source double taps are retained. No refresh delay or new input timer is added.

**CANCEL / H** now works during GPS loss, clears calibration without starting another job, and holds the burner amount. A later GPS fix does not restart an explicitly canceled run. Completed stop progress survives navigation pauses while the controller stays running; restarting the program or explicitly canceling still abandons the unfinished eight-stop session. The final saved brake model, 96-test survey, and burner heights retain their existing persistence. No extra checkpoint file is created.

After UPDATE to **v1.7.6**, open CALIBRATION and press **BRAKE CAL** directly, or F6 on the computer. Do not start FULL AUTO first. Wait through GPS pauses without canceling if you want to keep the current recorded count. After BRAKE CAL saves, use FULL AUTO CAL for the five flight validation tests. Regression coverage includes a long loss after one recorded stop, repeated missing fixes, recovery into the same job, cancellation with no GPS, direct Brake start, Full-then-Cancel, fixed button positions and presented-frame click targeting. An eight-stop simulation also completes after an injected navigation gap while retaining its first measurement. Actual modded GPU and GPS timing remains unverified in-game.

### v1.7.3 brake-calibration stop and settle fix

The reported restart of movement occurs during the eight BRAKE CAL stops. The old routine held full reverse until signed forward velocity was at most 0.15 blocks/s. That condition also accepted substantial backward velocity as a stop. It then tried to hold the exact coordinates at that instant with the navigation controller, even while reverse thrust was still decaying. This produced false stop records and a position-chasing rebound in simulation. With 0.65-second navigation samples and 0.8-second actuator response, the old routine failed to settle; it also failed with one-second samples and 1.2-second response. This reproduces a code defect without establishing the actual timing of the user's ship.

BRAKE CAL now releases full reverse before zero and finishes with proportional velocity damping. The damping includes bounded acceleration prediction to anticipate residual thrust, and accounts for polling time and the saved sensor delay. During the finish and settle phases it damps yaw rate without chasing the earlier position or heading. A stop is recorded only when total horizontal speed stays at most 0.2 blocks/s, absolute forward speed at most 0.15, and yaw rate below 0.03 rad/s for two seconds. Crossing zero or moving backward quickly cannot count. Reverse-force fitting uses only the full-reverse portion; the stopping distance includes the controlled finish. Reports distinguish `CAL_REVERSE` and `CAL_DAMP` commands.

The settling status now shows **0/8 recorded** through **8/8 recorded**. Acceleration after a recorded stop is intentional: the next speed/direction test is starting. Acceleration while repeatedly failing to settle at the same count is not expected. The current burner amount stays held; no altitude PID or burner sweep is added.

Three simulated eight-stop runs completed with no false stop records. Maximum speed after the first reading below 0.2 blocks/s, before the next intentional acceleration, was 0.245, 0.208 and 0.200 blocks/s for navigation/actuator timings of 0.30/0.25, 0.65/0.80 and 1.00/1.20 seconds respectively. Each run took about six simulated minutes. Small residual motion remains possible; this does not promise an instantaneous or exact-zero stop. Tests also reject a negative-velocity false stop and verify that a stationary ship is not driven back toward an earlier calibration point.

The fitted stopping distance now includes the gentler finish and can move braking earlier. Six flight scenarios still travelled from 15 to 3 blocks remaining in 4.2–6.0 simulated seconds; long-route cruise retains its existing thrust limits and has no new fixed speed cap. The pending-survey simulation passed all five flight tests without retries, with 0.363 blocks of scored overshoot versus 0.357 from physical position. Existing GPS, GPU, touch and cooperative-yield regressions also pass.

Press **H**, UPDATE to **v1.7.3**, then run **BRAKE CAL / F6** again. Keep `airship-autopilot-pending.cfg` and the saved 96-test survey. After BRAKE CAL saves, press **FULL AUTO CAL** to run only the five flight tests. Existing working calibration remains installed until replacement data is successfully saved. Actual in-game settling still needs confirmation; if it remains stuck, H then F8 provides the current phase, raw velocity and stop commands.

### v1.7.2 straight-route braking and observable test scoring

Measured braking previously returned before sideways route correction and pushed against the entire velocity vector. It could slow a sideways drift without steering back toward the intended line. Reverse braking now acts along the route while the existing lateral controller continues correcting sideways position and speed. Normal travel and each calibration leg use the same controller. The 24-thruster diagonal regression with 0.65-second samples and a pressure change now arrives in 59.8 simulated seconds versus 63.0 previously, without increased overshoot. This does not establish a globally fastest trajectory or reproduce the user's actual flight.

The five auto tests have separate waypoints around their starting point: +X, -X, +Z, -Z, then the origin. The full trail therefore includes reversals and diagonal legs. Each leg should follow its own direct line. The calibrated, settled five-leg simulation travels 1.0015 times the total direct leg distance; its scored overshoot is 0.417 blocks versus 0.408 from the simulator's physical position. Starting with substantial sideways velocity can still produce a curved recovery; the ship cannot instantly cancel momentum.

Overshoot is the positive signed projection `dot(position - goal, unit(goal - legStart))`. Sideways distance is separate, and being short of the target does not count as overshoot. The previous confirmation filter could forget an initial 1.9-block peak and record only the later 0.6-block sample when sustained overshoot became confirmed. It now retains that event's full peak. The 0.5-block threshold, 0.3-second confirmation and immediate retention above two blocks remain unchanged; a navigation gap clears unconfirmed evidence. Regression cases cover both axis signs, diagonals, translated coordinates, sideways offsets and transient versus sustained peaks. This fixes underreporting, not an established false rejection in the user's live run.

During flight tests the calibration panel shows **LEFT** (signed distance along the leg; negative means past the goal plane), **SIDE** (distance from the leg's line), and **OVER** (largest confirmed overshoot in that attempt). The ordinary test status now uses current GPS distance rather than the mean position of the last four seconds. That averaging remains in the settling check so briefly crossing the target cannot pass. Reports also include the three scoring fields. Boundary samples retain the destination and stage that produced their commands, instead of being mislabeled as the next test. Navigation gaps clear stale trace data. The DirectGPU panel, standard monitor and computer flight telemetry expose the geometry without changing the display backend or refresh scheduling.

After UPDATE, keep the saved 96-test and brake data. If BRAKE CAL has already saved, press FULL AUTO CAL to rerun only the five validation tests. Otherwise press BRAKE CAL / F6 first, then FULL AUTO CAL. If a test still fails or takes a detour, press H, then F8 and share that report; the live scoring and commands are needed to distinguish model error, lateral drift, GPS error and sensor delay. No new survey, burner sweep or peripheral is required by this update.

### v1.7.1 brake calibration before flight validation

v1.7.0 required a fully validated profile to start BRAKE CAL. This blocked ships whose 96-test survey was saved but whose five flight tests failed braking. BRAKE CAL now prefers the pending 96-test model when one exists, without requiring those five tests to pass. Its result is saved back to `airship-autopilot-pending.cfg`; normal AUTO remains unavailable for that candidate until flight validation succeeds. Press FULL AUTO CAL afterward to run only the five flight tests with the measured braking model. A validated working profile remains installed until the candidate passes. Failed or canceled brake measurement, and a failed save, retain the previous data.

Measured-model retries now increase the fitted stopping delay after overshoot. Previously retries increased only the legacy planner's response setting, which did not affect measured stopping speed. This moves braking earlier without lowering the cruise estimate. The regression simulation starts from an unvalidated survey, runs eight stops, then passes all five flight tests with 0.423 blocks of overshoot and no retries. Checks cover pending versus working saves, validation gating, survey preservation and save failure; actual in-game stopping remains unverified.

### v1.7.0 measured braking and faster approach

The old planner can demand very low speed well before arrival when a saved profile has accumulated conservative response settings. The new optional braking calibration measures reverse acceleration, coasting drag, and effective stopping delay in each ship direction. Its stopping model integrates `dv/dt = -force - drag * speed`, including distance traveled during the measured delay. Live air pressure scales the measured drag; current navigation polling time adds an allowance if readings arrive slower than during calibration. Height and the observed height range are saved with the pressure reference. There is no altitude PID or automatic burner sweep.

Navigation inverts that stopping curve to choose speed from remaining distance. Reverse thrust is proportional, with feedforward for the deceleration needed to follow the curve, rather than switching only between full power and zero. The last three blocks at low speed return to the existing precise hold. Calibrated braking uses velocity from the latest GPS interval: the previous extra velocity smoothing delayed corrections and caused a limit cycle in the 24-thruster, slow-polling simulation. Display speed/ETA smoothing remains unchanged. There is no fixed cruise speed cap.

#### Calibration order

1. **FULL AUTO CAL** first to measure the 96 thruster/nozzle responses. The five flight tests start automatically afterward. If those overshoot, press **H / HOLD** and continue with BRAKE CAL. If the 96 measurements are already saved for the current layout, do not repeat them. If FULL AUTO CAL already passed completely, you can still run BRAKE CAL to refine stopping.
2. At a stable burner level and normal cruising height, open **CALIBRATION → BRAKE CAL**, or press **F6** on the computer with no text box focused. The ship moves automatically in four directions, accelerating, coasting, accelerating again, then reversing to stop at two speeds per direction. Use clear air with hundreds of blocks of room in every horizontal direction and enough fuel. The current burner amount is held; the program does not change height to take measurements. The eight-stop routine took 260–335 simulated seconds; real time depends on the ship, GPS/hub sampling and settling. It does not return to its starting coordinates. **H / HOLD** cancels. A navigation interruption restarts the current measurement while retaining completed stops in memory; restarting the program requires restarting the eight-stop routine.
3. Wait for **BRAKE CAL saved**. If it says to run the five flight tests, press **FULL AUTO CAL**: it resumes only those tests using the saved thruster and braking measurements. After **FULL AUTO CAL saved**, enter a destination a few hundred blocks away and press **AUTO**. No second 96-test survey or burner sweep is required. Brake measurements are saved to the pending model if flight validation is still required, or directly inside `airship-autopilot.cfg` for an already validated model; both survive restart. Failure or cancellation keeps the working profile; a save failure also leaves it installed. Saved burner heights are preserved.

Run BRAKE CAL again after a load or propulsion change; changed thruster layout/names requires FULL AUTO CAL first. Pressure compensation uses a linear drag model measured at the calibration height, not a guarantee at every height, speed, fuel state or server delay. Testing at a substantially different height is still needed. The saved data contains eight small run summaries, not an accumulating raw recording. F8 flight reports now include predicted stopping distance, braking phase, and GPS interval velocity.

### v1.6.12 slightly later, stronger braking

The extra high-speed stopping allowance is reduced from 85% to 65% of velocity-loop response time, moving braking modestly closer to the destination. Once braking outside 20 blocks, correction now uses 50% of normal response time instead of 60%, making the unsaturated response to the same velocity error 20% stronger. Calibrated acceleration and thruster limits still apply. The six-block approach plan, near-destination damping, position hold, and uncapped long-route cruise are unchanged. Saved profiles and survey data remain usable after UPDATE. Regression checks compare the onset with v1.6.11 and verify the stronger correction; actual stopping distance still needs confirmation on the ship.

### v1.6.11 earlier braking with a moving final approach

High-speed planning now adds 85% of velocity-loop response time to its stopping allowance instead of 35%. When slowing outside 20 blocks, the velocity correction uses 60% of its normal response time, requesting stronger deceleration within the same calibrated acceleration and thruster limits. Acceleration away from the destination retains its normal response. Modern profiles no longer acquire a fixed cruise cap from `responseScale`: a failed braking test increases stopping caution instead of imposing an estimated cruise speed on long flights.

Inside 20 blocks, the route controller smoothly changes to a close-approach speed plan, fully taking over by six blocks. This plan retains the measured delay and acceleration limits but uses a 0.15-block stopping margin instead of the large high-speed caution margin. Its speed also tapers with remaining distance: about 1.2 blocks/second at six blocks for a stable profile, or about 0.72 for maximum caution, provided measured stopping authority permits it. These are requested speeds, not guaranteed actual speeds. The earlier blend into weak position hold could start as far as 24 blocks out on a cautious profile; velocity control now stays fully active to between 0.5 and 2 blocks, depending on caution. Position hold takes over only at the end. Close-approach braking keeps the normal velocity response to avoid oscillation from delayed samples.

Saved profiles and the 96-test survey remain usable after UPDATE. Per-test calibration retries, GPS range refinement, burner heights, and final cardinal alignment are retained. Automated checks cover strong deceleration, useful six-block approach commands, six-to-one-block transit, full long-route acceleration, mass/pressure variations, and the unbalanced/noisy case. They do not establish the ship's actual braking distance; share Esc, H, F8 output if overshoot remains in-game.

### v1.6.10 measured GPS range fitting

### v1.6.7 GPS jump filter recovery

### v1.6.1 command timing fix

The installed Create Propulsion 1.1.5 JAR marks liquid vector thruster `setVector` and `setThrustNormalized` as `@LuaFunction(mainThread=true)`. The previous output loop awaited these two calls for each of 24 thrusters sequentially. Corners could therefore receive the same control decision across many server ticks; the control loop also could not sample navigation again until all 48 waits finished. An instantaneous-thruster flight simulation did not exercise this delay. This is a confirmed serialization defect in the controller; its exact contribution to the reported wandering still needs in-game measurement.

v1.6.1 dispatches one CC `parallel.waitForAll` worker per thruster, so independent server-tick calls can progress together. Each worker preserves vector-before-power ordering, cooperative yields, and the cancellation check before sending power. Burner output is sent before the thruster batch. A regression scheduler with one tick per peripheral call now checks all 24 vector writes at tick 0 and all power writes at tick 1, completing after two ticks instead of 48 serial waits. Actual timing through the hub depends on its implementation and server load.

GPS velocity also previously divided travel distance by at most 1.5 seconds, even if the output/peripheral cycle took longer. That inflated speed and corrupted acceleration/drag estimates used for braking and calibration. GPS now uses the actual elapsed time; a separate three-second-cycle regression checks the resulting speed. Existing calibration files stay intact. In v1.6.1 the first recommendation was to retry the five auto tests using the saved measurements; v1.6.4 now requires a fresh GPS-checked survey first. In older versions, if the original survey ran with long peripheral cycles, its force/drag estimates may be biased and a fresh survey may still be needed. Preserve the old measurements until live flight confirms the fix.

The old travel PID limited speed to approximately `P / D * distance`, which could produce about 2 blocks/second with 24 blocks left. Repeated failed-arrival tests also reduced the saved cruise ceiling even when only the final position hold needed tuning. v1.6.0 uses a velocity controller along the original route, corrects sideways drift separately, and reserves acceleration for braking and lateral recovery. The original last-24-block position-hold blend was shortened for stable ships in v1.6.5; a short route cannot reach full cruise speed. Heading remains fixed during travel, and the final cardinal turn keeps the original destination coordinates.

After updating, press **FULL AUTO CAL** once. A pending model from v1.6.4 or later can reuse all saved thruster/nozzle measurements and run only the five auto tests. Older unchecked-GPS profiles require a new survey. The old controller's speed reductions are recalculated from the measured acceleration and drag. The previous working profile stays installed until validation passes; calibration files and saved heights are preserved. The longer auto-test legs allow acceleration and braking at cruise speed. Retuning changes velocity response as well as final hold gains; a slow, close arrival does not by itself cut the cruise ceiling.

## Full autopilot calibration

Connect all 24 `liquid_vector_thruster` devices, working wireless GPS, an Avionics `altitude_sensor`, `navigation_table`, and `gimbal_sensor`. The sensor and thrusters may be exposed through the supported wired/hub routes. Calibration measures the current ship and load; weight and thruster number positions do not need to be entered.

1. Get the ship airborne in a large open area: the faster cruise tests can travel hundreds of blocks from the start. Use a saved height or manual burner level to let it settle at your normal cruising height. Keep the gyroscope powered. Keep enough fuel for at least 40 minutes of automatic movement, allowing for the 24-thruster survey and retries.
2. Open **CALIBRATION** and press **FULL AUTO CAL**, or press **R** on the computer with no text box focused. It starts even if an old calibration already exists. No sweep is started. The current burner level is held throughout the procedure.
3. Let it finish: all 96 thruster/nozzle tests keep their six-second pulses and four-second coast measurement windows. Expect roughly 26 minutes for those measurements at normal sampling speed, plus five travel/braking validation legs; their length is calculated from the measured cruise speed, acceleration, and sensor delay so the tests can verify braking at full speed. Slower hub/GPS sampling increases the time. After the 96 tests the fitted candidate is checkpointed to `airship-autopilot-pending.cfg`. If validation is canceled, fails, or the computer restarts, press **FULL AUTO CAL** again to resume with the five auto tests only. Excessive overshoot or a failed arrival triggers retuning of the current test, with up to five attempts per test. RETURN moves back to that test's original starting point before its repeat. Earlier successful tests stay completed during the run, and passing test 5 saves and finishes; the displayed retry reason explains each extra attempt. If yaw rate exceeds 0.8 rad/s, calibration pauses with thruster commands off; press **HOLD** before retrying. Invalid GPS pauses outputs and restarts only the current thruster baseline, preserving completed tests. A gap over eight seconds restarts the current auto-validation leg; a GPS loss over six seconds cancels the current run while retaining any completed survey checkpoint. Actual time depends on the ship and server. Watch the displayed stage, remaining position error, and net drift. **CANCEL AUTO CAL**, **HOLD**, or **H** cancels; **STOP/S** also cuts burner output.
4. After **FULL AUTO CAL saved**, select a saved altitude, enter destination `X Z` on the computer, and press **AUTO/A**. The controller brakes using measured response, counters yaw through individual thruster commands, and keeps correcting position after arrival. At arrival it turns in place to the nearest of 0, 90, 180, or 270 degrees based on its actual heading, then holds position and altitude. It does not automatically lower the ship or touch down; choose a lower saved altitude separately. The calibration finish leaves the burner at its starting level until you choose another height or flight mode.

The measured model, tuned gains, pressure reference, and verification results are saved in `airship-autopilot.cfg` and loaded after restart. The unvalidated thruster model is checkpointed separately; it cannot engage autopilot until the auto tests pass. A failed or canceled run keeps the last working profile and lets **FULL AUTO CAL** resume validation from the checkpoint. Changed peripheral names invalidate the model. Recalibrate after changing mass/cargo, fuel type, thruster placement, propulsion settings, or upgrading to v1.5.0 for the 24-thruster setup. Autopilot learns a running correction for persistent horizontal drift and turning bias, estimates speed from a short position trend, and uses gimbal gravity to measure yaw rate accurately. Yaw drag compensation is bounded so an overestimated drag value cannot turn yaw damping into positive feedback. Validation measures net drift over several seconds and bounds individual position excursions. Calibration models horizontal movement and yaw, not active roll/pitch leveling; the gyro handles pitch/roll but does not hold heading. The optional **DIR CHECK/C** button only sends the old four wiring-check pulses and does not replace FULL AUTO CAL.

After updating to v1.5.0 or later, run FULL AUTO CAL once to rebuild the model for all 24 thrusters and replace the previous speed/power ceiling. Old profiles with the previous eight thruster names will be rejected automatically. The speed target comes from measured thrust, drag, and braking response; the controller retunes after overshoot or failed arrival rather than forcing a fixed slow cruise speed.

### Air pressure

Calibration measures drag at its current pressure. Autopilot scales that learned drag estimate with the live pressure reading and actively brakes instead of relying on coasting to stop. In thinner air it eases position/velocity feedback to avoid exciting rocking with delayed GPS readings; maximum cruise is determined by remaining stopping distance and available thrust. Both checked pack configs have `useAtmosphericPressure = false`, so this controller does not apply an invented inverse-pressure thrust boost. If the server changes that setting, or you fly under substantially different conditions, recalibrate at the intended cruise height. Pressure compensation is a learned approximation, not a guarantee across every altitude.

Height remains controlled by the burner map; FULL AUTO CAL does not generate or change that map. Run the separate sweep only when you need new saved heights.

FULL AUTO CAL chooses final position-hold P, I, and D automatically; straight-route cruise uses its separate measured velocity controller. Manual **SET PID** overrides are saved into the active profile; use the displayed measured gains as the starting point. Accepted ranges are P `0.0001–1`, I `0–0.05`, D `0–4`. ## DirectGPU startup hang: notes for future agents

Reported symptom: the computer remained at `Setting up display...` for minutes after the 24-thruster update. The confirmed controller defect was unbounded GPU setup before UI construction, followed by repeated setup attempts on failure. The progress message also covered the later UI construction, so that message alone never proved which GPU method stalled. Earlier claims that wired DirectGPU itself was definitely the cause were not verified in the running game.

History matters: v1.5.0 (`3a7f2b1`) did not change GPU setup from v1.4.2. Older commits repeatedly disabled and enabled it: `aeffe66` disabled GPU, `46b262a` enabled it with slower rendering, `4eb5381` blocked remote GPU, and `911a914` allowed wired GPU again. `bff1bab` added cooperative yields and progress messages, and `353bdd3` enabled mouse events. v1.5.1 disabled GPU globally; v1.5.2 simply enabled it again. Neither flag change established or fixed the underlying wait.

v1.5.3 keeps GPU enabled by default and gives setup an eight-second deadline through CC's `parallel.waitForAny`. Each step is printed and written to `airship-gpu.log` (replaced on each attempt). A setup error or a peripheral wait that exceeds the deadline disables retries for that run, reports the exact step, and opens the CC monitor fallback. Normal setup reuses an existing display (including ID `0`), creates at resolution scale `1` only when needed, checks positive pixel dimensions, and enables mouse events. `Building controls...` and `Starting flight panel...` distinguish later startup phases. Restarting the controller tries GPU again; no flight or burner calibration files are removed.

The local server-pack snapshot contains `directgpu-1.0.25-neoforge-1.21.1.jar`. Inspection of its `DirectGPUPeripheral` bytecode confirms `listDisplays`, `getDisplayInfo`, `autoDetectAndCreateDisplayWithResolution(1)`, and `enableMouseEvents(id,true,false)` match this setup. The create method accepts scale `1`; mouse setup returns void, so successful `pcall` is sufficient. This is evidence about the local snapshot, not confirmation of the active server version or an in-game reproduction.

The deadline works when a peripheral call yields while waiting for CC/server events. Lua cannot interrupt a Java method that blocks the entire computer thread without yielding. If that occurs, recover with Ctrl+T (or a computer reboot) and run `airship.lua --no-gpu` for one session, then inspect `airship-gpu.log` to find the last attempted method. If GPU reaches `ready` but startup still stalls, use the later phase messages to investigate UI construction or event-loop startup. Do not blanket-disable wired GPU or remove yielding checkpoints as a speculative fix. A native blocking method requires a mod-level investigation; this script does not patch the mod.

The next screenshot from v1.5.3 stopped specifically at `GPU: create display at resolution 1`, before `getDisplayInfo` or `enableMouseEvents`. That narrows the stalled call to unnamed `autoDetectAndCreateDisplayWithResolution(1)`. The eight-second Lua deadline did not resolve the reported stall. Bytecode inspection explains a costly path in that call: `resolveCreateMonitor` without a string argument invokes `detectNearestMonitorInfo(4)`, which invokes `autoDetectMonitorsInternal`. That method enumerates wired monitors and still loops over offsets -32 through 32 on all three axes, checking the radius-32 sphere for physical monitors. It may inspect a large region and repeatedly determine monitor geometry. The screenshot establishes the stalled API call; the exact internal operation still has not been profiled in the live game.

v1.5.4 bypasses that broad scan: it gets the discovered CC monitor's exact peripheral name and calls `autoDetectAndCreateDisplayWithResolution(monitorName, 1)`. In the inspected JAR, a nonempty string takes `detectNamedMonitor` instead of the broad nearest-monitor scan. The monitor name must be visible to DirectGPU on the wired network. Existing valid displays are still reused. If no exact monitor name is available, setup falls back with an explicit wiring message instead of calling the unnamed overload. Failed creation no longer calls `autoDetectMonitor` for diagnostics, since that would repeat the broad scan. Preserve these restrictions in future changes: no implicit unnamed fallback on creation failure. Regression tests check exact name and scale arguments and ensure failure never starts that diagnostic scan. In-game confirmation is still needed; the Java-call limitation above remains relevant.

Regression checks run from the repository root with Lua 5.2+: `lua airship/tests/gpu-startup.lua`, `lua airship/tests/yielding.lua`, and `lua airship/tests/navigation.lua`, and `lua airship/tests/gps.lua`. They cover new/reused display zero, resolution, cooperative setup timeout, malformed info, mouse setup failure, peripheral yielding, click routes, all display tabs, interrupted frames, and simulated navigation. They cannot establish actual GPU output, server timing, or flight behavior in Minecraft. Report those separately when publishing a fix.
